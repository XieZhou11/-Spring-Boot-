## 1. 范围与约定

本版共 27 张业务表，仅覆盖当前 MVP；不增加钱包、余额、提现、标签、多人邀约、运费或平台抽成。资金关系为：商品成交金额 = 买家实付金额 = 创作者应结算金额 = 全额退款金额。收货地址、发货运单号和模拟结算仍保留。

使用 MySQL 8.4 LTS / InnoDB / utf8mb4，默认排序规则 utf8mb4_0900_ai_ci。邮箱先去首尾空格、转小写后按二进制排序规则唯一；业务订单号、流水号、幂等键及运单号使用 ascii_bin；OSS 对象键区分大小写。所有关联由应用校验，**没有 FOREIGN KEY / REFERENCES 外键约束，也没有级联删除**；主键、唯一索引、CHECK 约束保留，用于单行取值和并发唯一性保底。

所有表主键为 `BIGINT UNSIGNED AUTO_INCREMENT`，数据库编号由服务端生成；对前端以字符串传输，避免 JavaScript 整数精度丢失。Java 使用正数 Long 范围，不使用 MySQL 无符号额外上半区。金额为 `DECIMAL(12,2)`，Java 用 BigDecimal，不用浮点；接口校验最多两位小数，不依赖数据库隐式舍入。时间用 `DATETIME(3)`，应用、JDBC 会话和数据库默认时间统一 Asia/Shanghai；自然日按北京时间，截止时刻使用服务器时间判断，达到截止即失效。

`NULL` 表示尚未产生或草稿未填写，不能用 0 伪造关联。布尔值为 `TINYINT UNSIGNED`，0 否、1 是。字段表“—”表示无默认值，调用方必须提供 NOT NULL 字段；“数据库生成”字段只读，应用不得写入。JSON 默认空数组时使用表达式 `DEFAULT (JSON_ARRAY())`。更新时间由数据库维护，原始事件时间及快照不随业务更新重写。

默认按主键查单，列表采用稳定的“业务时间 + id”排序及分页。批处理按截止时间和主键分批扫描，取得候选后进入业务事务重新检查状态，不因扫描读到候选就直接执行。

## 3. 索引与约束策略

每张表均有 `PRIMARY KEY (id)` 用于定位、行锁及稳定分页，下文逐表列出全部二级索引。`uk_` 为唯一索引，`idx_` 为普通索引。复合索引按主要等值条件、范围/排序字段组织；不因为字段名以 `_id` 结尾就机械建单列索引，不为低基数开关单独建索引。

MySQL 不提供通用的 WHERE 条件唯一索引，本版用可空的 STORED 生成列实现：满足业务状态时返回关联编号，否则返回 NULL，利用唯一索引允许多行 NULL 的行为。涉及默认地址、待审核/已通过认证、ACTIVE 报价、现货订单占用、待处理退款、每类成功流水、首次节点处理、待处理举报。生成列表达式见迁移文件；它们不能替代服务器时间检查及跨表归属校验。

本版没有为所有组合筛选排列建立索引。标题与描述的 `%关键词%` 检索不靠普通 B-tree 加速；按当前 MVP 规模先缩小可见候选再过滤，不额外引入全文分词。预算筛选、创作者资格、跨状态 IN、一级多子品类查询及“可购价格优先、其余作品靠后”的混合排序可能需要 filesort；不得声称现有索引完整消除了排序。相关业务开发在真实 MySQL 数据上用 EXPLAIN 和性能用例验证，必要时按实际 SQL 调整，尚无性能达标结论。

## 4. 逐表字段、索引及应用约束

字段的业务长度和明确数量范围来自需求；未规定长度的地址分段、技术标识等采用本版存储容量，供接口设计核对，不视为新增业务规则。未定义的尺寸图、认证作品每件图片、追加证据图片数量不擅自增加上限。通用图片按需求 3.3 为 jpg/jpeg/png/webp、单张最多 5MB；头像按 4.1.2 单独限制为 jpg/png、最多 2MB。全部 CHECK 表达式在迁移中定义；跨行数量、状态迁移、权限和 JSON 内部关联由应用负责。

## 5. JSON 数据约定与派生统计

JSON 用于有界图片集合及不可变快照，不代替有独立状态、分页、追加或并发唯一要求的业务表。保存文件编号数组，按数组顺序展示；接口中的编号统一字符串，服务端转换并校验正整数、去重、归属、文件可用状态及读取权限。SQL CHECK 只校验外层类型和已规定的数量，嵌套内容及引用存在性由应用校验。

| 字段/用途 | 结构约定与校验 |
| --- | --- |
| 各表 `*_image_ids`、`image_ids` | 文件编号的 JSON 字符串数组，例如 `["1001", "1002"]`；不存图片二进制或签名 URL。主图第一项是封面；图片数按所在业务字段要求校验。 |
| `creator_application.original_works` | 3—5 个对象的数组，每个对象包含 `finished_image_ids`、`process_image_ids` 两个编号数组；成品图至少一张、过程图至少一张。无需另建原创作品子表。 |
| `trade_order.address_snapshot` | 对象，包含 `recipient_name`、`phone`、`province`、`city`、`district`、`detail_address`；建单时从本人地址复制，之后不可覆盖。 |
| `trade_order.agreement_snapshot` | 对象，保存订单类型对应的品类路径及名称、材料、规格、描述、图片编号、交易条款文本/版本。定制另外保存需求用途/材料偏好/期望发货日、报价方案、补充约定、草图、定标时预计发货日及买家对日期偏差的明确确认依据；现货保存原作品内容。金额、工期、标题使用已有独立字段，不在 JSON 中另维护一套可变金额。 |
| `order_settlement.payee_snapshot` | 对象，含 `approved_application_id`、`real_name`、`alipay_account_ciphertext`；姓名明文，账号是可解密的带版本密文编码（如 Base64），不能仅脱敏保存。支付成功取已通过申请一次复制，结算时校验原快照，历史不随其他资料更新。 |
| `system_notification.business_reference` | 对象，按事件包含必要的 `order_id`、`request_id`、`work_id`、`report_id` 等引用，编号字符串；仅用于定位，不授予对象权限。 |
| `operation_log.detail` | 对象，按动作存必要前后值、审核依据及旧内容快照，例如单号更正 `old_tracking_no` / `new_tracking_no`。仅保留业务必需内容，旧快照与文件访问继承对应对象权限。 |

不新增独立统计表或预计算计数列。点赞、收藏、关注由关系表计数；评分与好评率由可见且关联订单未退款的评价计算。平均分按需求保留一位小数，4—5 星为好评，无有效评价返回“暂无评价”。完成订单数依据 `original_completed_at IS NOT NULL` 且当前未退款的实际完成事实，不能只查 `status = 'COMPLETED'` 而漏掉暂在售后的已完成订单。

待结算汇总只含 PENDING，已结算汇总只含 SETTLED，CANCELLED 不计入两者。交易额、退款额按需求统计口径由成功资金流水及订单状态计算，不覆盖原金额来“扣掉退款”；统计日期范围使用 `[start, end)`，避免在索引时间列上套 DATE 函数。

## 6. 应用事务、并发与异常回滚

本章规定后续服务实现应遵守的事务边界，**本次没有实现或执行这些业务事务**。数据库关联从应用层约束，不表示“先查询存在、稍后随意写入”即可；必须在同一事务内重新验证真实归属、资格、当前状态和截止时间，再锁定或带原状态条件更新。被历史业务引用的账号、已发布内容、申请、订单、证据与资金记录不做任意物理删除；草稿删除、地址删除、文件清理分别按上述限制处理。

### 6.1 服务事务与锁定顺序

交易服务入口建议明确使用 `@Transactional(rollbackFor = Exception.class, isolation = Isolation.READ_COMMITTED)`；选择 READ COMMITTED 是为在等待用户/需求锁后读取最新已提交的额度及状态。若改用 MySQL 默认 REPEATABLE READ，额度计数等必须采用正确的当前读方案，不能复用加锁前已建立的旧快照。事务入口须经过 Spring 代理，不能依靠类内自调用生效；关键步骤不能拆入异步线程。受影响行数不符合预期、关系失效、唯一冲突、SQL 异常及业务校验失败时抛出异常并回滚，不能 catch 后返回成功、继续提交其他变更。

统一按以下顺序获取本次所需的**已有行锁**，不涉及的对象跳过，同类多行按编号升序：

```text
品类（如需，先共享锁并校验层级/启用状态）
→ 用户 → 作品 → 需求 → 报价 → 订单 → 退款申请
→ 结算记录 → 制作节点 → 会话 → 文件
→ 新增资金流水 / 通知 / 操作日志等结果记录
```

普通查询可先解析不可变关联编号，但加锁后必须重检，不能相信加锁前的状态。对一对多报价/会话按固定顺序锁定；所有 HTTP、WebSocket、管理员操作和定时任务复用同样顺序。涉及作品与其现货订单时先锁作品再锁订单，避免付款与手动恢复库存反向等待。涉及审核申请、举报等对象时，先锁相关账号及内容主对象，再锁申请/举报记录，随后写通知和日志；后台品类变更也遵守同一顺序，不反向申请上游锁。

用户行锁用于串行化每日首次发作品、每日报价、同时开放需求和地址数量等校验：锁对应用户，使用当前自然日范围或当前状态计数，然后写入。报价还须锁需求，先把已经到期的 ACTIVE 报价置失效，再检查最多五份和同人一份。接口与定时任务都检查服务器时间，不能把生成列唯一索引当作自动过期机制。

唯一键冲突、死锁或锁等待超时应使整个事务失败；不能在已失败的事务内接着写。幂等重试在事务外根据已有业务结果核对账号和请求内容；必要的有限重试须重跑完整事务并保持同一业务幂等标识，不重发通知或重复记账。文件绑定和清理都锁文件行，防止检查未引用后被并发绑定再删除；OSS 删除在提交后执行并保留重试状态。

### 6.2 必须一起成功或回滚的业务操作

| 操作 | 同一事务内的校验与变更 | 失败回滚结果 |
| --- | --- | --- |
| 验证码消费与注册/重置 | 锁当前验证码，校验 SENT、未用、未过期；创建账号或更新密码并标记 used_at。重置提交后撤销本机旧 Session 和连接。 | 账号变化与验证码消费均回滚；提交后内存会话撤销应补偿，不能把已改密码的旧 Session 保留为有效。 |
| 认证提交/撤回/审核 | 锁账号、申请，校验材料及主品类；新增申请/关联或更新结论，同步账号状态、通过申请引用，保存通知与日志。 | 不留下“账号已认证但申请未通过”或半份主品类。 |
| 默认地址切换 | 锁用户与目标地址，校验归属；取消原默认，设置目标默认。 | 任一步失败恢复原默认，不出现中间状态被当作成功。 |
| 作品首次提交/审核/修改 | 锁账号、作品及所需来源订单，校验首次提交额度、授权、文件与开关；设置首次提交时间/审核状态，写日志及通知。 | 不扣掉首次提交额度，也不留下已公开但未经审核的修改。 |
| 需求发布/关闭/过期 | 锁账号、需求与有关报价，校验开放数量、定向资格、时效；改需求、失效报价、仅归档无订单会话，保存通知/日志。 | 需求状态、报价和会话可写性一起恢复。 |
| 报价提交/撤回/到期 | 锁创作者、需求、报价，失效过期项，校验每日/每需求额度及定向关系，新增或更新报价并重算 OPEN/QUOTING/EXPIRED，保存通知。 | 需求与报价状态一致，不保留超额有效报价。 |
| 定标建单 | 校验买家地址、唯一有效报价、资格及预计发货偏差确认；锁相关账号、来源作品（如需）、需求及报价；定标、唯一建单、地址/合同快照、落选结果、关联或创建中标会话、归档落选会话及通知/日志。 | 建单失败则本次定标不生效，不出现已定标无订单。 |
| 现货建单 | 锁双方账号与作品，校验资格、上架、销售开关及 AVAILABLE；按价格快照建单，作品改 RESERVED 并指向订单，建立会话。 | 订单、库存占用、会话均回滚；失败不占库存。 |
| 支付 | 锁有关作品/需求/订单，校验待付款、24 小时截止及条款；暂停新业务不阻止已有订单付款。成功支付流水、paid_at、现货 SOLD_OUT+待发货或定制待开工、约定发货截止、定制五节点初始计划、PENDING 结算和账户快照、需求 IN_TRADE、通知/日志一起保存。 | 不保留成功流水或半付款状态；资金失败尝试如需留存，在回滚后另存 FAILED。 |
| 未付款取消/超时 | 与支付锁同一订单；只从 PENDING_PAY 条件变更，释放现货占用或关闭定制需求，保存通知/日志。 | 支付和取消只有一个成功；已付订单不能走未付款释放库存。 |
| 开工/节点/发货 | 锁订单及节点，校验非售后/终态及顺序；节点初次记录、下一节点解锁、状态和通知一起写。第五节点图文+运单号+shipped_at+auto_confirm_at 同时生效。 | 不出现 5/5 已完成却未发货，或打卡保存但状态未推进。 |
| 运单号更正 | 校验已发货未确认且当前允许操作；更新单号、记录旧新值/操作者/时间并通知买家。 | 单号、日志、通知一起回滚；原发货及自动确认时刻不改。 |
| 普通退款申请 | 锁订单及相关退款、结算；重检原完成七天窗口、未退款未结算且无处理中申请；新增 WAIT_ADMIN，记录 original_order_status，订单进入 AFTER_SALE，通知双方。 | 不出现售后中无申请或申请已占用而订单仍能发货。 |
| 无责超时退款/普通批准 | 锁相关作品/需求、订单、申请及结算；无责分支重检支付满 48 小时仍未开工，普通分支核实退回或免退依据；成功退款流水、申请 REFUNDED、订单 REFUNDED、定制需求 CLOSED、结算 CANCELLED 与 cancelled_at、通知/日志一起保存。 | 退款流水、履约终止和取消待结算任一步失败全部回滚；原支付金额及证据不覆盖。现货不自动重售。 |
| 驳回或撤回退款 | 锁订单和申请，校验 WAIT_ADMIN；申请终结并恢复 original_order_status，只有恢复 SHIPPED 才将 auto_confirm_at 增加本次 finished_at-created_at；保留 original_completed_at、原发货截止和节点计划。 | 状态和本次顺延一起回滚，重复请求不能重复加时。 |
| 确认收货/自动确认 | 锁订单，重检 SHIPPED、无处理中售后及相应截止；置 COMPLETED，仅首次写 original_completed_at，保存通知/日志。 | 不提前开放评价/结算，也不重置已存在的原完成时间。 |

| 发送消息/已读 | 锁会话并重检业务可写性；发送时校验幂等、分配下一 seq_no、持久消息及更新最近消息时间；已读用 GREATEST 等方式只向前更新本人游标。 | 保存消息失败则序号和列表时间也回滚，不推送“已发送成功”。 |
| 成品公开申请/回复 | 订单行锁下重检身份与状态，NONE→PENDING 仅已完成定制创作者可做；PENDING→APPROVED/REJECTED 仅本买家可做，同时保存时间、通知和日志。 | 失败不留下缺通知的授权变化；已有最终回复不覆盖，未回复不会自动同意。 |
| 举报及内容治理 | 锁目标及举报，重复处理中举报追加证据；结论、内容可见性/统一暂停标记、必要旧值快照、通知及日志同事务保存。 | 不出现治理已生效但无依据记录；恢复不能抹去用户自删或其他独立处置。 |

申请退款、结算、发货、节点推进、收货与自动确认均在订单锁后再校验状态。仅对业务主表做一次提前查询、随后单独写流水，无法满足本设计的一致性要求。售后结束后原完成窗口已届满、无其他处理中申请时，可由相同事务服务或下一轮扫描结算，不能重开七天窗口。

### 6.3 明确的 COMMIT / ROLLBACK 分支

以默认地址切换为例，以下为服务调用参数化 SQL 的事务示意，`:user_id` / `:address_id` 是绑定参数，**不是 Flyway 迁移语法，也不在本次执行**：

```sql
START TRANSACTION;
SELECT id FROM user_account WHERE id = :user_id FOR UPDATE;
SELECT id, user_id FROM shipping_address WHERE id = :address_id FOR UPDATE;
-- 应用验证用户存在、目标存在且确属本人；不满足则进入下方异常分支。
UPDATE shipping_address SET is_default = 0
WHERE user_id = :user_id AND is_default = 1;
UPDATE shipping_address SET is_default = 1
WHERE id = :address_id AND user_id = :user_id;
-- 目标设置失败或出现 SQL/唯一约束异常，不能继续提交。
COMMIT;
```

上面仅为成功分支；业务校验或 SQL 异常走独立的异常分支：

```sql
ROLLBACK;
-- 服务端继续抛出异常，统一返回失败；不能吞掉异常后返回成功。
```

不是先 COMMIT 再 ROLLBACK。Spring 实际实现由事务管理器完成提交/回滚，无需在 MyBatis 中手工混用上述事务语句。`rollbackFor = Exception.class` 覆盖受检异常；异常必须到达事务代理或明确标记 rollback-only，统一异常响应应在事务服务外转换。

数据库内的业务结果、通知、成功操作日志一起提交；WebSocket 确认与推送在提交后进行，推送失败保留记录供重连补拉。SMTP、OSS、内存 Session 与数据库不是同一事务：上传/邮件失败需如实更新状态并执行补偿，已经发出的邮件或已删的 OSS 对象不能被数据库 ROLLBACK 撤销。失败尝试日志若需保留，在原事务回滚后用独立事务保存，不与待回滚事务混写。

## 7. Flyway 文件位置与结构回退

### 7.1 正向迁移

文件：`backend/src/main/resources/db/migration/V1__create_mvp_tables.sql`。使用 Flyway 标准版本命名与默认 `classpath:db/migration` 路径，27 条 CREATE TABLE，不创建 database、数据库用户、测试数据或 Flyway 自身历史表。本次不配置连接、不移除当前启动类对数据源及 Flyway 的自动配置排除，不启动应用，也不执行 migrate/validate/repair/clean。

### 7.2 业务事务回滚与结构回退的区别

MySQL 8.4 的 CREATE TABLE / DROP TABLE 等 DDL 会隐式提交，不能用 `START TRANSACTION` 包住 27 条 CREATE TABLE 并承诺失败后全部撤销。单条 DDL 的原子性不等于整批 Flyway 迁移的事务原子性；迁移中途失败可能留下此前已创建表，必须核对实际 schema 与 Flyway 记录。

已另备 `backend/src/main/resources/db/rollback/V1__create_mvp_tables.rollback.sql`，含逆序的 27 条 `DROP TABLE IF EXISTS`，**仅供未来人工确认目标后处理无业务数据的专用初始化库或可丢弃残留**。它会删除表内数据，不提供多表整体原子回退。该目录不在默认迁移扫描路径，不能加入 `flyway.locations`；不使用 V2 删除表作为自动回退，不假设已购买或支持 Flyway Undo。

存在业务数据时使用经评估的补偿迁移或备份恢复，不执行初始化删表脚本。完整 V1 已登记成功后，单纯手动删表不会撤销 Flyway 版本；专用空库通常重建后重新初始化。失败迁移先核对并清理本次实际残留，再依据真实历史状态决定是否人工 repair；repair 只维护历史元数据，不恢复数据库结构。两份 SQL 都不删除/修改 `flyway_schema_history`，不执行 clean。
