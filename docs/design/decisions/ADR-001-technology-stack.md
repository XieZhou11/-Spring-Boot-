## 1. 背景与选择标准

项目为本科毕业设计，面向 PC Chrome、Edge，当前仅有前后端骨架，尚无可运行业务系统。需求以单机 50 并发、500 件作品、200 条需求、300 笔订单、20000 条消息作为性能测试参考。选型目标是完成全部首版业务、方便开发调试，并能解释和验证权限、事务、并发与实时消息。

定标必须同时确定唯一报价并创建唯一订单；单件现货不能重复售出；模拟资金动作仍须幂等。邮箱必须实际发送，聊天和通知必须保存后实时推送。性能指标须通过后续实测判定，不能由选用框架直接推断达标。

## 3. 备选方案与取舍

| 方案 | 优点 | 代价与结论 |
| --- | --- | --- |
| 原生内存 HttpSession（采用） | 沿用 Servlet 和 Spring Security 的会话能力，组件少、易调试 | 适用于单机，应用重启后登录态丢失；符合当前简化会话管理的要求 |
| Spring Session JDBC（备选） | 利用已有 MySQL 跨重启保存会话 | 额外引入会话表、清理和集成配置，当前不需要 |
| 聊天与通知共用 WebSocket（推荐） | 复用登录鉴权、连接、重连与事件分发逻辑 | 客户端维护一个连接管理模块，以事件类型区分处理 |
| 聊天 WebSocket + 通知 SSE（当前不采用） | SSE 适合单向文本推送，浏览器 EventSource 自带断线重连能力 | 需要维护两条长期连接及两套连接处理逻辑；当前没有通知独立扩展或兼容方面的需求 |

首版采用单体应用内的业务服务协作，不增加微服务、消息中间件或分布式事务组件。关键词检索按需求使用 MySQL 标题与描述匹配及分页；当前无需分词搜索系统。文件按用户要求使用 OSS，由后端直接调用官方 Java SDK；超时处理使用 Spring Scheduling。

## 4. 关键实现约定

### 4.1 登录与资格

登录使用 Tomcat 原生内存 HttpSession，不引入 Spring Session 或额外会话存储服务。不可预测的 Session ID 通过 HttpOnly Cookie 携带。开发时 Vite 代理 HTTP 和 WebSocket 请求，浏览器按同源方式访问；配置可信 Origin、Cookie 属性和 CSRF 防护。适用 HTTPS 的环境启用 Secure Cookie。会话登记与短期限流只服务单机；应用重启清空登录态，用户重新登录，数据库中的业务和消息记录保留。

7 天有效期按登录签发时刻保存截止时间并校验，Cookie 和容器空闲超时配置不能把它缩短为默认 30 分钟，也不能因滑动续期无限延长。退出使对应 Session 失效并关闭关联连接；维护本机账号与登录 Session 的登记，密码重置后将该账号所有旧 Session 失效并断开旧连接。HTTP 请求及 WebSocket 业务操作均检查登录有效性，不只在握手时认证。

身份切换只更新当前 Session 的默认视图；认证资格属于账号。暂停新业务仍保留旧订单履约和沟通权限。注册和重置共用按邮箱保存的验证码，在 MySQL 保存摘要、有效期和消费/发送状态，并原子消费；重发使该邮箱旧码失效。已按用户决定取消验证码发送间隔、每日额度、用途区分及连续密码错误锁定，全部业务页面须登录后访问。邮件或数据库操作失败返回可见错误，不能假成功。

聊天的 60 秒窗口、重复文本检测和超限暂停使用有界的单机内存记录，按发送账号与会话聚合，多个连接共用同一计数；并发更新须原子化，定时清除过期条目。此类短期限流记录重启后重置；每日作品、报价等业务额度按数据库记录和事务校验。

### 4.2 事务、金额与状态

定标、现货锁定、付款、退款和结算使用 Spring 本地事务、MySQL 行锁或带原状态的条件更新，并配合数据库唯一约束。操作先校验身份、归属、状态和截止时间，再改变数据；幂等重试返回同一业务结果。涉及多个对象时约定一致的加锁顺序。交易正确性由数据库事务及约束保证。

按用户约束不使用数据库外键，由应用在同一事务内校验关联、归属和状态；保留主键、唯一索引及 CHECK。服务入口显式设置异常回滚，关键更新失败须抛出异常，不能返回成功并提交部分结果。具体锁定顺序、27 张表的字段与索引见[数据库表结构](../数据库表结构.md)。MySQL DDL 隐式提交，业务事务回滚不等于整批建表回退；人工结构回退独立于 Flyway 自动扫描，SQL 均尚未执行。

金额使用 Java `BigDecimal` 和 MySQL `DECIMAL`，人民币保存到分。接口金额使用十进制字符串，商品成交金额与买家实付金额以服务端确定的订单快照为准；应结算金额和全额退款金额均等于实付金额。保存需求规定的金额、方案、完整地址和收款账户等快照。状态采用明确枚举和业务迁移方法，现货与定制分别校验合法路径；结算前全额退款时，在同一事务中取消待结算。

定制成品公开授权保存在订单上，记录授权状态、申请时间和回复时间，由订单创作者申请、订单买家通过按钮明确回复；作品保存来源订单编号。案例提交及修改时校验授权、归属和交易开关，按需求进行作品审核，不以聊天消息推断授权。

### 4.3 消息与超时恢复

聊天和系统通知共用一套 WebSocket 通道。Vue 应用登录后建立连接，跨页面复用，不为聊天页和通知铃铛分别建连接。事件通过 `type` 区分，例如 `CHAT_MESSAGE`、`SYSTEM_NOTIFICATION`、`UNREAD_UPDATED`；每条事件带相应记录编号和必要业务引用，具体字段随消息任务确定。系统通知只支持查看、标已读和跳转业务，使用双向通道不代表通知可以回复。

SSE 是服务端向浏览器单向推送的方式，适合独立通知流，自动重连是它的便利之处。已有聊天 WebSocket 时，也能直接用同一连接向浏览器推送通知；同时引入 SSE 不会自动提高可靠性，反而增加连接、鉴权和重连的维护成本。因此首版推荐统一 WebSocket，不另建 SSE 通道。通知列表、历史分页、断线补拉和标已读使用普通 HTTP 接口；HTTP 查询与实时推送各有用途。

业务通知与业务变更在同一数据库事务保存；聊天持久化提交后才向发送方确认成功并推送。推送失败保留数据库记录，客户端重连或登录时分页补拉，按唯一消息号去重；已读游标由服务端维护并同步多端。发送请求带客户端幂等标识，避免超时重试形成重复消息。

WebSocket 从已登录 Session 确定账号，不接收客户端自报身份作为授权依据。握手、消息发送、会话查询和图片访问均验证业务关系；未形成订单且需求关闭/过期、或定标未中标的会话归档只读，中标原会话关联订单继续使用。已成单会话不因订单完成、取消、退款或关联需求关闭而归档，双方仍可沟通和补证，但不能重开已结束的业务窗口。权限变化与归档后立即按当前规则限制操作。Session 到期、退出或密码重置后旧连接不再具有业务权限。

定时任务按数据库中截止时间分页查找，使用原状态条件及唯一事件键保证重复执行不重复关单、退款、提醒或结算。重启后继续处理已到期事项。付款、定标和报价等接口也检查服务器时间，不能依赖扫描任务恰好执行。扫描间隔和提醒延迟在对应任务确定并验证，不改变需求规定的业务期限。

### 4.4 文件、隐私与外部能力

图片由浏览器提交给后端，后端检查实际文件类型、可解析性、大小和数量，再通过阿里云 OSS 官方 Java SDK 上传。服务端生成唯一 Object Key，MySQL 保存 Object Key、文件类型、大小、上传人及业务关联，不把会过期的签名 URL 作为永久地址。上传失败返回明确错误，不把未成功上传的文件标为可用；OSS 写入和数据库写入不是同一事务，出现部分成功时记录并重试补偿或清理本次未关联对象。

OSS 使用私有 Bucket。公开作品图可由公开接口在验证作品可见性后签发短时访问 URL；认证材料、会话图片和退款凭证必须先验证登录与业务关系，再签发短时访问 URL。应用长期访问密钥只放后端环境配置，不能进入前端或版本库；首版采用后端转传，暂不增加浏览器直传和临时凭证流程。OSS SDK 已锁定并完成 JDK 21 下的依赖构建检查；实际上传及运行兼容性仍在图片功能任务验证。

真实姓名按用户决定明文保存，支付宝账户使用带版本的认证加密（如 JDK AES-GCM），密钥通过环境配置提供。两者均按角色最小返回并脱敏，结算快照保持相同存储约定。

邮件通过真实 SMTP 验证收信和发送失败；支付、退款、结算按需求模拟但保留真实业务状态和流水。不接入真实支付、打款、物流轨迹、实名认证或图片智能审核服务。
